# Tryal
The product is called **Tryal** (renamed from "Trial"; user-facing text only). Code, DB values and identifiers keep the old name: the stored status is `'trial'`, tables/RPCs/migrations/notification types, the slug, bundle identifier, scheme and EAS project are unchanged and must not be renamed. All user-visible strings say "Tryal" (screens, notifications, permission texts, share text, errors); scripts/test-brand-name.mjs fails if "Trial" comes back into one. Wordmarks: expo/assets/images/tryal-wordmark.png on light screens, tryal-wordmark-white.png on dark ones (trial-wordmark.png is kept, unused).

There is no follower system. Distribution is **stranger-only, platform-wide, not a setting**: "known people" are phone contacts (a match in either direction), email matches (hashed; Apple relay addresses just never match), friends, plus the creator's hide list (view `known_connections`, one server-side source of truth; raw address books are never stored, only HMAC hashes). Known people never get your posts in any feed or discovery surface (get_feed_engine, Explore, creator search, suggested creators), testing or survived, and never count toward a verdict; the checks live in the database (`trial_creators_who_know`, RLS `posts_testing_not_for_known`), the client has no fallback around them. Anyone can still open a creator's profile and see survived posts (profile_posts), and `search_people` (adding friends) and the hide-list picker are unfiltered. The hide list is private and does not block messaging. A creator can send their OWN posts to friends in DMs; nobody can send someone else's post to a known connection of its creator (chat_can_send_post / chat_post_available). friend_test_optin and the known_source_friends switch were removed; the only exception is **Spotlight** (migration-spotlight.sql): an admin (spotlight_admins, the owner; admin screen app/spotlight-admin.tsx) offers a creator one survived post in a category (Creator of the Day, Rising Creators, Most Creative, Best Storytelling, Most Improved, Community Favorite); NOTHING is shown to anyone until the creator answers: full (the picked post may also reach friends/contacts, never the hide list), strangers-only (the known-connections rule stays), or decline. One function, spotlight_eligible, is the exposure rule for the Spotlight section (Explore), the feed boost (spotlight posts lead an eligible viewer's feed for spotlight_hours) and the profile badge (badge_days). Rotation: the same creator is not offered again within rotation_days (a decline counts); config in spotlight_config (rotation_days 30, offer_hours 72, spotlight_hours 72, badge_days 30). No payments; the offer is an in-app notification (spotlight_offer), no push.

Three systems: AI video editor, content testing, a fresh feed. Core loop: upload video -> edit choice (app/edit-choice.tsx: Keep original / AI edit / Customize; nothing is edited before it, the editor runs only what was chosen, see lib/editChoice.ts) -> AI edit -> Post ("Put it on Tryal") -> tested by strangers -> survives -> 24-hour distribution -> expires. No follower/following system; no groups and no comments. Friends (mutual: invite link, request, or username) can send each other 1:1 text messages and posts (supabase/migration-friends-messages.sql); friends are known people. Profile = username, picture, bio, external links (Instagram, TikTok, YouTube, website), not a grid of all videos. Navigation: Feed, Create/AI Editor, Profile.

## Stack
React Native + Expo + TypeScript, Supabase (SQL migrations in expo/supabase/), EAS builds. Run all EAS/expo commands from expo/.

## Lifecycle (times calculated server-side, never from the device clock)
testing (up to max_test_hours, default 72 h) -> survived, or 'unjudged' (kept, only the creator sees it) when too few strangers saw it, or deleted if judged and failed;  survived (in the 24-hour boost window, then stays on the creator's profile and, as a fallback, in strangers' feeds) -> never expires. A post that fails is deleted. (Older text below about archive/expiry applies to posts created before stranger-only.) Original: testing -> survived (active for 24 hours) -> expired. Stored status for testing is 'trial'; a post is active while status = 'survived' and distribution_expires_at > now() (there is no active_24h status). A post that does not survive is archived (shown to the creator as "Tryal ended"). Stored: testing_started_at, survived_at, distribution_started_at, distribution_expires_at, expired_at. Expired and archived posts leave every feed. Post metadata and metrics are kept; the large video file is deleted later (about 7 days after expiry) by a scheduled job, only after a dry run. Reactions expire with their parent post and never get their own verdict. A reaction cannot be published to an expired post.

## Verdict rule (live: migration-trial-engine.sql, overridden by expo/supabase/migration-stranger-only.sql; run_trial_engine every 5 minutes)
Only strangers count: the creator, phone/email contacts, friends and the hide list are never in the test audience and never in the verdict. Each stranger who sees the post gets a score 0..1: watched 6 s or half (0.4), finished (0.3), like (0.3), share (0.5), video reaction (0.6), capped at 1. The post is judged against a bar (0.30, moving to the median of recent posts once there are enough; failed posts leave anonymous rows in trial_bar_samples so the bar survives their deletion) with a Bayesian test; audiences grow in stages (cohorts). Survive needs ALSO at least max(1, 5% of viewers) strangers who liked, shared or reacted (min_active, min_active_fraction): watching alone never survives. Not enough strangers to judge it is NOT a failure: the post stays on trial and keeps being distributed until a hard cap (trial_engine_config.max_test_hours, default 72 h from posting, enforced by trigger zzz_trial_cap_checkpoint). At the cap: fewer than min_exhausted_viewers (5) strangers saw it -> status **'unjudged'** (new value, not survived, not failed): kept, never deleted, no longer distributed, visible only to its creator (own profile, "On Tryal" tab with a NOT ENOUGH VIEWS badge; RLS posts_unjudged_owner_only), and the creator gets a verdict_unjudged notification ("Not enough people saw this yet."; in-app only, no push). With enough strangers it survives if it meets the bar (with the active minimum), otherwise it is failed. Only a post that was actually JUDGED and failed is fully deleted (NEW posts only): row, reactions, likes, notifications and the media (queued for storage deletion); survived and unjudged posts are never deleted; old archived/incomplete rows are left alone. All thresholds live in trial_engine_config. Run-through: scripts/test-trial-engine-sql.mjs (baseline) and scripts/test-stranger-only-sql.mjs (live rules). Live definitions overridden by migration-stranger-only.sql (last in MIGRATIONS_ORDER.txt, after migration-live-snapshot.sql which records what was live). (The older N-views rule on branch verdict-at-n-views is not used.)

## Feed
Discovery first, popularity second (get_feed_engine in migration-stranger-only.sql). Every tier excludes the viewer's known people and the viewer's own posts. Order: every testing post assigned to the viewer first (oldest first, round-robin across creators), then a few survived posts from creators the viewer engages with (affinity boost), then survived posts still in their 24 h window, then older survived posts (still stranger-only) as a fallback, then "all caught up": unseen before seen, each creator's best survived post before anyone's second, most liked first (strangers' likes + survived_reaction_weight x video reactions; the creator's own never count). Survived posts stay on the creator's profile permanently. After posting, the user lands in the feed.

## Notifications
In-app rows are created in SQL. Push (Expo): post survived, reaction on my post, likes only as milestones (1st, 5, 10, 25), optional "trial ended". No follower notifications.

## Cost rules
Process once, store the final asset, serve it, expire it. No paid AI API in the core product. The editor works on-device and deterministically: silence detection (native module expo/modules/audio-loudness, thresholds in expo/lib/silenceDetection.ts), cuts saved as segments/trim_data instructions, never re-rendering. Captions later via on-device speech recognition. Local files: temporary video files (post_uploads/, thumbnails/, Caches/Camera, ImagePicker, render_*.mp4, tmp/) are deleted after a successful post and by the launch cleanup (lib/storageCleanup.ts); drafts and files referenced by saved drafts or pending uploads are never deleted. Automatic only (no button).

## Working rules
Minimal edits, reuse existing code. One commit per numbered item. SQL changes are idempotent migration files in expo/supabase/ that I run manually in the Supabase SQL editor; the latest migration defining run_survival_checkpoint supersedes earlier ones and older ones must never be re-run. Never commit .env or keys. Native changes (new native modules, plugins, app.json permissions, icons, SDK upgrades) need a new EAS build and a version bump in app.json (runtime policy is appVersion, not fingerprint); JS-only changes can ship with eas update. Do not blindly delete DropDay code: audit dependencies first, hide or disable before deleting, and keep tables until a migration plan exists.
- Never rename existing statuses or notification types; add new values instead.
- No text comments in the app; conversations happen through video reactions.
